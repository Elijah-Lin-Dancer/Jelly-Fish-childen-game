# Phase 11 方案 · 开放世界（含海岸带）

> 目标：把游戏从"一片固定海域的水族箱"升级为**可移动探索的开放世界**——横向可沿岸行走、纵向从**陆地沙滩一路走到深海无光区**，沿途风景、地貌、物种、人类活动全部随位置变化。
>
> 这是 Phase 10「向我的世界看齐」的第二块：Phase 10 做了**开篇体验**（标题屏 / 新建世界 / 群系 / 种子 / 伴随水母），Phase 11 做**开放世界本身**——空间、地形生成、相机、移动、海岸带与人类元素。
>
> 沿用零构建 / ES Module / Canvas2D 架构，复用 Phase 10 的群系系统、种子系统、伴随水母与物种权重，不破坏已上线的 Phase 1–10。

## 0. 设计依据（真实世界 + MC 开放世界模型）

| 参考 | 借鉴点 |
|---|---|
| Minecraft 开放世界 | 世界有坐标、只见当前视野、边缘即未知；**种子决定地形生成**，同种子同世界、可复现可分享；生物群系按空间分布，走过去才展开 |
| 真实海岸剖面 | 陆→沙滩→浅滩(涉水)→近海礁区→中深→深海无光区，是一条**水深梯度**；海岸线有石岸/沙岸/沙洲等形态 |
| 真实海洋分布 | 群系按**温度带**分布（暖水→冷水→冻洋），冷热渐变而非硬切；**深海热泉**是洋中脊海底裂缝的特殊地貌 |
| MC 蘑菇岛 | 罕见、孤立、无掠食者——对应我们罕见的**蘑菇海** |

## 1. 核心概念：两层正交的坐标系

世界的两个轴各自承担一种"变化"，正交叠加——正好对应 MC 的「生物群系 × 高度」：

```
        岸线（陆地/水交界）
  ↑水深  ─────────────────────────────────►  worldX = 沿岸走向 / 温度带（暖→冷）
  浅     🏖 沙滩   🌊 浅滩(涉水)   🐠 近海礁区
         🚶 人类活动带（游泳者/小船/码头）
         🐟 中深水域（鱼群/海龟/水母主体）
  深     ⬛ 深海无光区（热泉/极地/发光种）
```

- **worldY = 水深梯度**（纵向）：决定"岸 / 浅 / 近海 / 中深 / 深海"。
- **worldX = 沿岸景致 / 温度带**（横向）：决定"珊瑚礁 / 荧光湾 / 热泉区 / 极地"等群系气质。
- 两者共同决定：水色、能见度、氛围、物种权重、装饰、人类元素密度。

## 2. 世界尺度与相机

> **实施修订（11A 落地后回填）**：世界尺寸最终定为 **3200 × 1400**，不是初稿的 6000。
> 原因是一条硬约束：相机缩放 `scale ≈ 视口宽 / 世界宽`，所以**世界越大画面缩得越小**，
> 而水母尺寸决定点击互动的命中难度。实测（桌面 16:9）：
>
> | 世界宽 | 缩放 | 横移距离 | 观感 |
> |---|---|---|---|
> | 3200 | 0.59 | 1.6 屏 | 接近 1:1，水下沉浸感强 ← 选定 |
> | 5200 | 0.35 | 3 屏 | 能看出地形走势，水母偏小 |
> | 9000 | 0.23 | 5 屏 | 俯瞰长卷，水母成小点，互动体验崩 |
>
> 另有一条数学性质必须记录：`scale = max(宽比, 高比)` 会让约束边「恰好铺满」，
> 该方向余量恒为 0（桌面 16:9 横向锁死、手机竖屏纵向锁死），**调 w/h 无法解决**。
> 相机因此乘了一个 `GROW = 1.15`，把 scale 抬到两个比值之上，四向才有行程。

| 项 | 取值 | 说明 |
|---|---|---|
| 世界横向 | `worldX ∈ [0, 3200]` | 桌面约 1.6 屏、手机竖屏约 5.7 屏 |
| 世界纵向 | `worldY ∈ [-180, 1220]` | `worldY<0` 为水面以上的陆地带；0 为水平面；>0 为水下深度 |
| 相机 | `camera = {x, y}`，屏幕是取景框 | 绘制时 `ctx.translate(-camera.x, -camera.y)` |
| 移动方式 | **拖动/平移为主 + 键盘方向键（WASD/箭头）** | 拖动 = 直接平移世界；键盘 = 匀速平移 |
| 边界 | 相机做 clamp，不超出世界范围 | 世界边缘是"探索的尽头" |

> 保留现有 `view.W/H`（屏幕尺寸）；新增 `camera.x/y`（世界坐标视窗左上角）。所有实体用世界坐标，绘制时统一减去相机偏移。

## 3. 地形生成（种子驱动）· `js/systems/terrain.js` 新增

**三种岸线地形类型**，由种子或玩家"地形"选项决定（同种子同地形，可复现分享）：

| terrain id | 名称 | 长相 | 出生点 |
|---|---|---|---|
| `shore` | 顶部水平岸线 | 顶部一条横贯沙滩，往下逐深——经典海湾 | 岸线附近的浅滩 |
| `slope` | 左岸斜向深入 | 左上是陆地，岸线斜着往右下推入深海 | 岸线中段的浅滩 |
| `island` | 中央小岛 | 中央一座小岛（你的家），四周环形变深 | 岛上 |

- `createTerrain({ type, seed })` 返回地形实例，暴露：
  - `depthAt(x, y)` → 该点的"水深 / 陆地"值（负=陆地海拔，正=水下深度）。
  - `zoneAt(x, y)` → 分类：`'land' | 'beach' | 'shallow' | 'nearshore' | 'midsea' | 'deepsea'`。
  - `shoreLineAt(x)` → 该 x 处的水陆交界 y（用于画岸线与出生点）。
  - `surfaceAt(x)` → 水面/地面的绘制高度。
- **实现**：以种子 PRNG 派生少量正弦/噪声参数（岸线基准高度、斜率、岛屿半径与偏移、沙滩宽度抖动），保证平滑、可复现、无外部依赖。

### 水深带定义（纵向 5 带 + 陆地带）

| 带 | `zoneAt` | 视觉 | 主要元素 |
|---|---|---|---|
| 陆地带 | `land` | 沙地、礁石、栈道、灯塔剪影 | 沙滩伞、棕榈、贝壳、海鸥 |
| 沙滩 | `beach` | 沙岸、浪花线 | 海鸥、贝壳、遮阳伞 |
| 浅滩(涉水) | `shallow` | 阳光透底、浅绿 | **游泳者、戏水小孩、救生圈**、小船 |
| 近海礁区 | `nearshore` | 珊瑚、明亮 | 珊瑚礁、鱼群、海龟 |
| 中深水域 | `midsea` | 光线渐暗 | 鱼群、水母主体 |
| 深海无光区 | `deepsea` | 暗、发光点 | 热泉、极地冰海、稀有发光种 |

> **实施修订（11A 落地后回填）**：阈值按「每档约占可见高度的 1/6」标定。
> 桌面 16:9 可见高约 1130，故六档取 `land<0 / beach<150 / shallow<380 /
> nearshore<700 / midsea<1030 / deepsea<MAX_DEPTH(1400)`。
> 实测分布：shore 陆地 9–18%、slope 22–32%、island 11–19%，三型都能进深海。

## 4. 群系 × 水深 的叠加规则 · `js/systems/worlds.js` 扩展

Phase 10 的 5 个群系（珊瑚礁 / 极地冰海 / 深海热泉 / 荧光湾 / 蘑菇海）继续存在，但**只在"水下带"生效**，且按 `worldX`（温度带）分布：

- **横向分布（沿温度带，遵循自然界）**：左暖右冷——
  `珊瑚礁(暖) → 荧光湾(温带过渡) → 深海热泉(洋中脊，偏深) → 极地冰海(冷)`；相邻群系之间是**平滑渐变过渡**（水色/物种权重插值，非硬切）。
- **纵向适配**：群系的水色/物种权重随水深带做修正——
  - 浅滩：所有群系都更亮更暖，珊瑚礁最盛；
  - 深海：水色统一压暗，只有 `deepsea` 带才出现热泉/极地/稀有发光种；
  - 蘑菇海：**罕见孤立区**（种子 <0.5% 在深水带某段生成），无掠食者。
- `biomeAt(x, y)` → 返回该点的实际群系（含横向渐变 blend + 纵向修正）。

> 复用 Phase 10：`worlds.js` 的群系定义（baseTint / haze / rays / feature / weight / mechanics）、`seed.js` 的 PRNG、`speciesWeight`。新增的是"按坐标采样 + 过渡插值"。

## 5. 陆地与人类层 · `js/entities/life.js` 新增

近岸带出现**人类与生活元素**（纯程序化 Canvas 绘制，清淡剪影感，不喧宾夺主），全部**可点击轻互动**：

| 元素 | 出现带 | 互动（点击） |
|---|---|---|
| 游泳的人 | 浅滩 | 挥手 + 溅水花 |
| 戏水小孩 | 浅滩 | 蹦跳 + 水花 |
| 救生圈 | 浅滩 | 晃动 + 涟漪 |
| 小船 / 帆船 | 浅滩/近海 | 鸣笛（气泡 + 轻音效）+ 轻微摇晃 |
| 栈桥 / 码头 | 岸带 | 无（静态结构） |
| 灯塔 | 岸带 | 旋转光束闪一下 |
| 沙滩遮阳伞 / 棕榈 | 岸带 | 轻微摆动 |
| 海鸥 | 岸带/水面 | 惊飞飞走 |
| 贝壳 | 沙滩 | 拾起（+1 收集计数 / 小提示） |

- `createLife({ terrain, seed })` 按地形与种子**确定性**布点（同种子同布点）。
- 只生成**镜头可见范围内**的元素（视口裁剪，见 §8）。
- 数据驱动：每类元素一个绘制 + 一个 `onTap`，便于扩展。
- 音效复用 Phase 9 的 `audio.sfx(name)`（新增 `seagull` / `horn` / `splash` 等少量）。

## 6. 移动与操作

| 操作 | 行为 |
|---|---|
| 拖动（pointer drag） | 平移到世界（拖动方向 = 世界移动方向的反向，直觉式） |
| 键盘 WASD / ←→↑↓ | 匀速平移相机（含惯性缓动） |
| 点击水面 | 现有交互不变（气泡/召唤/互动水母） |
| 点击人类元素 | 触发其轻互动（挥手 / 鸣笛 / 惊飞…） |

- 移动只改 `camera`，不改实体世界坐标 —— 世界是"固定存在"的，你只是走过去。
- 平移有轻微**缓动 + 边界阻尼**，手感柔和（契合禅意调性）。
- 移动端：单指拖动平移；保留原有 tap 交互判定（拖动阈值区分）。

- **发现机制**：首次进入某水深带 / 某群系段 → `hud.toast` 提示 + 记入探索图鉴（复用现有 `explore`）。

  - `slope`：岸线中段浅滩；
  - `island`：岛中央（家）。
- **家的概念**：出生点即"巢穴"，可放置初始建筑（复用 Phase 8 建造）。

## 8. 性能对策（关键）

Canvas2D 做"更大的世界"最怕全量绘制。对策：

1. **视口裁剪**：实体 / 装饰只在 `camera` 可视矩形（外扩一屏缓冲）内更新与绘制；世界坐标 → 屏幕坐标统一变换。
2. **分带更新频率**：远景陆地/海鸥等低频更新；水母/鱼群等高频，仅可见者。
3. **地形按需采样**：`depthAt/zoneAt` 用解析式（正弦/噪声），O(1) 计算，不预生成大网格。
4. **背景渐变缓存**：沿用现有按主题/尺寸缓存的渐变；尺寸不变不重建。
5. **画质分级联动**：沿用 `quality` 分级，低配时减少人类元素密度与装饰数量。
6. **对象池复用**：人类元素用固定池，进出视口时启用/停用，不频繁 new。

## 13. 分期建议（降低风险）

体量较大，建议**分两批上线**：

- **11A**：世界坐标 + 相机 + 拖动/方向键移动 + 地形生成（3 种岸线）+ 水深带 + 岸线/水面渲染 + 存档 v4。**先让"能走的世界"跑起来。**
- **11B**：人类与生活元素（游泳者/船/灯塔/海鸥/贝壳…）+ 可点击轻互动 + 新建世界地形选项与缩略图升级 + 发现机制打磨。

### 11B 实施修订（落地后回填）

**世界尺寸与相机：3200 × 1400 → 3200 × 4000。**

11B 做发现机制时暴露了一个 11A 遗留的结构性问题：**六档水深带实际只能用五档**。
`deepsea` 阈值 1030，但相机中心能到达的最深处只有 ~850（`midsea`），
「抵达深海」这条发现永远刷不出来。同一根因的另一半更严重 ——
**手机竖屏进游戏看到的是一片没有岸的空海**（实测首屏 95% 是 midsea/deepsea，
岸上元素全在视野上方）。

根因有两层，都不是「参数没调好」：

1. **纯 `max` 缩放会让紧边恰好铺满。** 竖屏时「高」是紧边，于是 `vh ≈ 世界高`，
   相机被夹在一条窄缝里，水线进不了可达范围。
   ⚠ 靠放大世界解决不了：世界变高 → `vh` 同比变大 → 需求一起涨。
   数值求解过这个不动点，要求 `h ≈ 7400` —— 世界会变成一条细长海沟。
   **真正的解法是给 scale 加下界**：`camera.js` 新增 `FILL_MAX = 0.72`，
   规定单轴可见范围最多占世界的 72%，把「紧边」也松开。

2. **地形公式的设计基准必须与世界几何解耦。** 引入常量 `SEA_SPAN = 1900`
   作为岛屿半径 / 斜坡落差 / 水深剖面的标定基准。
   ⚠ 它**不等于** `WORLD.y1`。曾经让 `SEA_SPAN = WORLD.y1`，
   于是每次调整世界几何都会重塑地貌（拉深水底 → 岛半径同比放大 → 岛被推出屏幕，
   岛心相对位置从 +0.42 掉到 -0.36）。钉成常量后，调几何不再动地貌。

`homePoint()` 的契约也统一成 `{ x, y, span }`：三种地形都只返回构图锚点，
相机偏移由 `goHome` 取 `max(span * 0.5, vh * 0.26)` ——
小景（平岸/斜岸）按视口走，大景（孤岛）按景物尺寸走，新增地形自动获得合理构图。

### 上线后回填：两个渲染缺陷 + 一个行为瑕疵

部署完成后按种子抽查截图，发现代码本身没问题但**画面是错的**。
三个问题都不是参数问题，而是判据/假设用错了地方。

**① 陆地渲染成一块纯色矩形。** `scenery.js` 里
`createLinearGradient(0, 0, 0, view.H * 0.5)` 的终点与陆地多边形实际
高度无关；一旦陆地超过半屏，下半屏全部落在最后一个色标上，
于是沙色在离水线不远处被硬切断，变成与水面毫无呼应的一整块。
**修法**：先累加多边形的真实纵向跨度 `landTop` / `landBot`，
把渐变锚到 `min(landTop,0) - view.H` → `max(landBot,1)`。
语义固定为 `0` = 最内陆（暗）、`1` = 紧贴水线（亮沙），
暖沙色只占最后约 15%。

**② 岸上元素全挤在水线上方几十像素的一条窄带里。** 一屏能看到约
1296 世界单位的高度，而 `pushAshore` 原来的逻辑是「跨过水线就停」。
**修法**：目标改成**离水线的绝对距离**，由 `ahead` 直接映射
`targetDepth = -(60 + ahead * 0.7)`。
⚠ 中间踩过两次坑：先按**增量**推进 —— 结果层次反了
（遮阳伞 ahead 130 到 -911，灯塔 ahead 320 才 -409），
因为增量耦合了「它在哪个带被采样」；随后用固定
`SAFE_DEPTH = 200` 兜底 —— 又把所有元素压到同一深度。
最终统一为绝对目标深度。

**③ 岸上元素仍会入水（756 个里 2 个，都是海鸥）。**
排查出这是**两个独立原因**，先被我误判成同一个：

- *投放点确实在水里*：按岸线**法向**推进依赖法向正确性，而岸线在
  弯曲处法向会失真（shore 的正弦+fbm 扰动、island 的 `islWobble`）。
  ⚠ 这里的关键认知是：`depthAt(x,y) < 0` 才是「在陆地上」的**权威判据**
  （它内部走 `landHeightAt`，与地形渲染同源）；
  `shoreLineAt(x)` 只是水线基准线，拿它二次判会与 `depthAt` 打架。
  **修法**：放弃方向迭代，改成**纯 y 向扫描** ——
  `depthAt` 关于 y 在近岸是单调的（越往内陆越负），
  从水下起点向上扫，取首个 `depth <= targetDepth` 的 y。
  与 x 方向的岸线形状彻底解耦，也不依赖收敛假设。
  该列没有足够深的陆地（窄岛）时退回「刚出水再进 30」。
  顺带给 slope 补上真实岸线法向：`shoreBaseAt` 带
  `(x - sx0) * slopeA` 的线性倾斜，仍按 `(0,-1)` 垂直推会沿坡面横向
  漂移、最终落到水线以下。

- *投放点没错，是海鸥自己飞走的*：`Seagull.update()` 每帧
  `x += vx`，没有边界。同一只鸟 **0.5s 时 (1497, -26) 深度 -20（在岸上 ✓），
  6.5s 时 (1277, -48) 深度 +38（在水里 ✗）** —— 它只是横飞 220 单位
  落到了一个水线更高的弯。
  **教训**：「是否入水」的断言**必须在投放瞬间采样**，
  因为 `Seagull` / `Swimmer` / `Boat` / `Lifebuoy` 之后都会移动。
  按 700ms 静置重测后：756 个岸上元素 **0 个在投放时入水**。
  **修法**：给海鸥加 `homeX` + `range`（260~520）巡航锚点，
  到达半径就掉头，绕自己的领地打转（也更像真的）。
  加约束前 42 秒 X 轨迹是单向漂移约 1000 单位，加约束后
  在 1090~1670 之间往返振荡约 580 单位。

## 上线后回填（三）：竖屏纵向锁死 + 手机虚拟摇杆

用户报告「电脑端 W/A/S/D 和方向键都无法移动场景」。诊断链路：
`keydown` → `heldKeys` → `refreshKeyAxis` → `camInput`（state 单例）
→ `loop` 每帧 `cam.update(dt)` 读它推进 `tx/ty`。逻辑完整。

**实测结论（无头 Chromium 真实引擎，指向本地与线上同一份代码）：**

| 视口 | 横向 | 纵向↓(S) | 纵向↑(W/↑) | 初始相机 ty |
| --- | --- | --- | --- | --- |
| 1280×720 | ✅ | ✅ | ✅ | −284（有上方余量） |
| 1000×1000 | ✅ | ✅ | ✅ | 正常 |
| 900×1200 | ✅ | ✅ | ❌ 锁死 | **−1100 = minY（贴顶）** |
| 414×896 | ✅ | ✅ | ❌ 锁死 | **−1100 = minY** |

- **横屏四向全动**，代码无 bug。用户「标准横屏全屏完全不动」与实测冲突，
  归环境（中文输入法激活吞字母键、页面/标签页未聚焦、或 Pages 缓存旧 JS）。
- **竖屏/近方视口（h/w ≥ ~1.2）：纵向↑被边界钉死** —— 这是真实 bug，
  对手机竖屏是致命的（手机本就没有键盘）。

**根因**：`goHome`（`main.js`）把期望相机**中心** `cy` 直接 `clamp` 到
`[minY, maxY]`；但 `camera.bounds` 的 `minY/maxY` 是相机**左上角 `ty`** 的范围，
与中心差半个视口高 `vh/2`。竖屏 `vh` 大时 `cy` 被压到 `maxY`，
经 `centerOn(ty = cy - vh/2)` 换算后 `ty` 溢出 `minY` 被夹回最上界 ——
相机初始贴 Y 上界，向上零余量；只有向下/左右能动。
`coach.js` 只处理 `Escape`，不是吞键元凶（W 不动是边界 clamp，非事件未达）。

**修法**：`cy` 改 clamp 到**中心范围** `[minY + vh/2, maxY + vh/2]`。
竖屏初始 `ty` 由 −1100 → −588（居中），上/下都留余量，W/↑ 走通；
横屏 `cy` 本就在范围内，行为不变。

**手机虚拟摇杆（仿 Minecraft 左摇杆）**：`js/ui/touchPad.js`，
左下角固定 thumbstick，pointer 拖动向量写入新 state `touchAxis`；
`camera.update` 每帧把 `camInput`（键盘）+ `touchAxis` 合成（并存、互不覆盖）。
方向语义与键盘一致（上推 = 负 y = 相机向上）。仅在
`isMobile || matchMedia('(pointer: coarse)')` 时构建 DOM，桌面鼠标无开销。

**键盘健壮性防御**：`home.enter()` 进入游戏时 `document.activeElement.blur()`，
防止创建面板的种子/名字输入框焦点残留导致 `onKeyDown` 的 `isTypingTarget`
把全部键吞掉（表现为「进游戏后键盘全失灵」）。

**线上验证**（真实 URL，无头）：横屏四向动；竖屏 `ArrowUp` 首键 `ty −604 → −433`
（向上可动）；触屏 context 摇杆 DOM 存在且 `.show`，上推 `ty−360`、右推 `tx+360`
均有效；桌面无摇杆 DOM；0 pageerror。关键文件与线上 sha256 全部一致。
